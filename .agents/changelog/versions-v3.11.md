- **v3.11.2** — Stale recs cache across module graphs FIX: `recommendationsCache` becomes a `globalThis` singleton (August 15, 2026):
  - **Why**: during the v3.11.1 live-verify the page still showed **"Last updated: 14/8/2026"** right after the fix re-ran the recommendations and the worker called `invalidateRecommendationsCache()` — the run completed but the public API kept serving the stale cached run. Root cause: Next.js dev (Turbopack) loads `instrumentation.ts` (worker/cron daemon) and API routes as **SEPARATE module graphs**, so `lib/cache.ts` was evaluated TWICE → two independent `recommendationsCache` NodeCache instances. The worker's `flushAll()` (via `invalidateRecommendationsCache`) cleared ITS copy; the API route (running in the other module graph) still held the 23h-old `latest` entry and served it.
  - **Fix (`lib/cache.ts`)**: `recommendationsCache` now lives on `globalThis` under `__recommendationsCache` — `globalForCache.__recommendationsCache ?? (globalForCache.__recommendationsCache = new NodeCache({...}))` — exactly the `lib/prisma.ts` singleton pattern. Every importer (`dailyRecommendationService.ts`, `recommendationPerformanceService.ts` — the only two) resolves the SAME instance, so worker invalidation is immediately visible to the route. The other caches (main/hot/static/historical) are UNCHANGED — short TTLs and no cross-module invalidation semantics.
  - **Tests**: NEW `lib/__tests__/cacheSingleton.test.ts` (4) — `jest.resetModules()` + re-`require` simulates two module graphs: (1) same-instance identity across two loads; (2) value set in load A visible in load B; (3) **worker→route regression** — `flushAll` in load B invalidates what load A cached (`get` undefined + `keys()` empty); (4) `keys()` reflects writes from both instances. `afterEach` deletes the globalThis key so tests don't leak.
  - **Verification**: **Suite 700 pass** (was 696; 54 suites + 1 skipped pre-existing). `npx tsc --noEmit` 71 = exact pre-existing baseline, 0 new errors. No UI change → no Playwright re-run needed.
  - **Files Created**: `lib/__tests__/cacheSingleton.test.ts`.
  - **Files Modified**: `lib/cache.ts` (globalThis singleton for `recommendationsCache` only), `AGENTS.md`, `.agents/CHANGELOG.md`, `.agents/changelog/versions-v3.md`, `TODO.md`, `Lessons.md` (#76), `Primer.md`, `agent-memory.md`, `.agents/session-todos.md`, `.agents/sessions/2026-08-14-b35eca4/` (decisions + flow).

- **v3.11.0** — In-Process node-cron Cron Daemon (replaces Netlify scheduled functions) + `daysTracked` sort fix + carried committed-unreleased v3.10.1 batch (August 15, 2026):
  - **Why**: the Netlify scheduled-function cron was fragile — serverless isolates die per request, the ledger writers lived inside the deleted functions, and any future "spawn a daemon on cold start" fix would fan out per isolate. The 4 system crons (Daily Recommendations 10:00 IST, Performance Check 15:30 IST, Market Sync 06:31 IST, AI Connection Test) now run on **node-cron inside the persistent Next.js server** (`next start` / `npm run dev`) via NEW root `instrumentation.ts` — `register()` guarded by `NEXT_RUNTIME === "nodejs"`, `NEXT_PHASE !== "phase-production-build"`, and `CRON_DAEMON_DISABLED=1` opt-out (documented for Netlify serverless, where every isolate dies after a request).
