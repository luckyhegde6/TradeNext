- **v3.7.2** — Netlify Secrets-Scan Build-Failure Fix (Config + App Hygiene) + Live-Site Health/Live-Site-Staleness Finding (August 13, 2026):
  - **Symptom (user-reported)**: Netlify build failed — "Secrets scanning found secrets in build." The scanner flags EVERY repo file (not just deployed paths) and any literal that looks like a credential (bot tokens, chat IDs, numeric placeholders) trips it.
  - **Root cause 1 — `.githooks/` not omit-listed**: `netlify.toml` `SECRETS_SCAN_OMIT_PATHS` already listed `AGENTS.md`, `README.md`, `prisma/seed.ts` etc., but the **`.githooks/commit-msg`** hook (extensionless file — the scanner's include patterns don't exempt it) still contained demo-credential literals (redacted to `********`) from the v3.5.7 credential-masking work. Every build after that change therefore failed the scan.
  - **Fix 1**: `netlify.toml` — appended `.githooks` to `SECRETS_SCAN_OMIT_PATHS` (config-only; the hooks themselves are unchanged and keep enforcing credential hygiene).
  - **Root cause 2 — placeholder-looking numeric secrets in app code**: grep sweep found numeric literals that LOOK like real secrets in scanned paths — `lib/alerts/delivery/telegram.ts` example `botToken`/`chatId` constants, `TelegramSubscription.tsx` placeholder chatId, `app/api/user/telegram/verify/route.ts` JSDoc example verification code, `lib/__tests__/nse-api.test.ts` fixture timestamps. Even though none were real credentials, any FUTURE env value containing that numeric substring (e.g. a rotated password `…123456…`) would match the literal and fail the build — and they read as leaked secrets.
