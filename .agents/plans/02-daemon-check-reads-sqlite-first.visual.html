TradeNext — SQLite-First Daemon Check-Reads

The 30s worker poll and 5-min cron resync hammered Prisma with high-frequency check-reads on every Netlify instance. User directive: “i only want to write these to the prisma during the 12hr sync job. if sqlite is empty then fetch from the prisma but write to sqlite.” Daemon check-reads move to the local SQLite mirror; Prisma is written only at the 12h reconcile, while every cross-instance atomic op (claim, leader lock) stays on Prisma.

v3.25.0 branch fix/cron-breaker-leader poll read → SQLite cron resync → SQLite claim + leader stay Prisma 12h reconcile

1 · The Problem

Daemon loopCadenceImpact
worker-engine pollevery 30s✕ A pending-task read hits Prisma on EVERY tick, on EVERY instance (10+ cold-start bursts) — the dominant Accelerate op-count driver.
cron-daemon resyncevery 5 min✕ Re-fetches the whole active cron-job list just to catch expression changes.
task-status writesper completion⚠ completed/failed status updates written straight to Prisma.
periodic heartbeatevery 5 min⚠ pingLiveness() already SQLite-only since v3.22.0 — the model to extend.
Directive scope: move ONLY the high-frequency daemon check-reads + task-status writes off Prisma. Every cross-instance atomic exclusion / coordination read stays on Prisma — the claim, the leader lock + its heartbeat, reaper liveness, stateless-transition heartbeats, and fireJob re-fetch.

2 · SQLite-First Read Tier

NEW discoverPendingTask() (worker-engine) and SQLite-first syncCronJobs() (cron-daemon) read the local mirror first; when the mirror is empty/stale they fall back to Prisma AND seed SQLite (upsertWorkerTask / upsertCronJob) so the next poll is SQLite-only.

3 · What Moves vs What Stays

Moves to SQLite (local mirror)Stays on Prisma (shared truth)
✔ Worker poll pending-task read
✔ Cron 5-min resync job-list read
✔ Task completion/failure writes
✔ Periodic pingLiveness() heartbeat (v3.22.0)		 ✔ Atomic task claim (updateMany)
✔ Leader lock + heartbeat (split-leadership guard)
✔ Reaper liveness reads (cross-instance view)
✔ Stateless-transition heartbeat (busy/idle)
✔ fireJob authoritative re-fetch
Why these final divergences? (recorded in the plan)
  • Reaper liveness stays Prisma — a local per-instance mirror only holds THIS process's data; serving liveness from it would blind the reaper to other instances and risk reaping their live work (the v3.12.0 prod bug).
  • Leader lock + heartbeat stay Prisma — they ARE the cross-instance coordination primitive (PR #113 split-leadership bug); a standby would otherwise claim a stale leader.
  • Admin route mirroring not done — low-frequency user actions; seedTaskMirror already covers poll-visibility for freshly created tasks.

4 · SQLite → Prisma Reconcile (the ONLY daemon-table writes)

NEW reconcileControlToPrisma(db) runs at the top of syncFromPrisma() (12h cadence, leader-gated) and batch-pushes the local control-plane diffs to Prisma in a handful of ops.
