TradeNext — Screener & AI Optimization

Free-tier OpenRouter was exhausted (50 req/day), the connection-test cron burned 28–42 req/day, and Chartink throttle-bursts starved the screener. Fixes: 429 early-exit (no retry on exhausted quota), a 2-hour connection-test skip window, parallelized screener DB reads, and a 8192 maxTokens default.

2 · 429 Early-Exit (no retry)

In recommendation-agent.ts analyzeBatch() and swing-agent.ts: when a batch returns HTTP 429, set the stopAllBatches flag, log, and fail the remaining batches immediately — no retry, no fallback, no wasted budget.

(no retry, no fallback)
        A->>A: fail-fast — return rolled-up result
    else other non-429 error
        P->>A: retry ×2 with backoff (unchanged)
    end
Rule: 429 means “today's budget is gone” — retrying only makes it worse. Non-429 transient errors keep the existing ×2 retry.

3 · Connection-Test Skip Window (2h)

NEW shouldSkipConnectionTest() in connectionTestService.ts — reads the last ServerLog (source="ai", action="connection_test", status="ok") from Prisma; if within 2h, skip the test entirely. DB error → return false (run the test) — never throws. Wired into the cron daemon's spawnDueCronJob().

4 · AI Pre-Flight Gate & Misc Fixes

  • Pre-flight gate — before the daily run, runAiConnectionTest(120s): ok → configured model · fallback → run on recommended model · failed → skipAi = true (all-HOLD with aiSuccess:false) — fail fast instead of burning the 14-min cap.
  • maxTokens default → 8192 — getPromptTimeoutMs() clamp per batch remaining budget; 30s cap → 120s (AI_PROMPT_TIMEOUT_MS).
  • Parallel screener reads — 234 serial DB reads batched into parallel queries.
  • Chartink HTTP 419 throttle — burst-aware scanning with TradingView fallback (v3.5.6 runner).
  • ⚠ Caveat: DB ai_config metadata overrides env default until re-saved (config load order).
