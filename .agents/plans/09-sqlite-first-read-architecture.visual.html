TradeNext — SQLite-First NSE Read Architecture

Architecture revamp: pages read from NSE (rate-disciplined) + SQLite mirror first; Prisma demoted to backup · auth · boot-hydration; the recurring sync is a one-way SQLite → Prisma push every 6h (boot is the ONLY Prisma → SQLite pull).

NSE fetch → SQLite SQLite-first reads Prisma = backup + auth NSE anti-blacklist discipline Boot hydration — ONLY pull (every instance) 6h leader PUSH (one-way) _sync_outbox change tracking

1 · The Problem

Today Prisma/Postgres is the primary tier for almost every read and write — so DB hiccups cascade into 500s / empty screens / breaker trips, and NSE data is mirrored into Prisma at high frequency for no benefit.

Symptom (prod evidence)Root cause
"SQLite Not Ready" on prod db-health✕ Netlify never ships sql-wasm.wasm — copy-sql-wasm-netlify.mjs is never run by the build (publish=".next"), so initSqlJs throws → ready:false forever.
DB op-count pressure / plan-limit breaker trips✕ Every NSE sync also mirrors to Prisma (flushNseToPrisma at 3 call sites + a 60s startNsePromoteFlush timer). High-frequency writes for data Prisma doesn't own.
"Recent Sync History" empty after restart✕ Sync history lives in-memory only (state.syncHistory) — lost on every deploy.
NSE 403s / 419s / blacklist risk⚠ Burst NSE calls (market sync, historical backfill, screener scans) with no single-flight / min-interval guard.
Multi-instance cold-start bursts✕ Boot hydration is leader-gated — only ONE instance hydrates SQLite; the rest serve stale mirrors.
User directive: pages less reliant on the DB, more on NSE fetch + SQLite — but avoid frequent/high-frequency NSE calls to avoid blacklisting; Prisma as backup + auth + initial bootup hydration (recommendations, swing, performance, audit, worker status, AI configs, auth sessions); only low-frequency data syncs.

2 · Target Architecture

Two read tiers: market data (NSE → SQLite cache, never Prisma) and derived data (SQLite mirror → Prisma fallback). Jobs + admin CRUD write SQLite + _sync_outbox; Prisma is authoritative for auth, and receives data only at the 6h push.

3 · Boot Hydration — Every Instance

At register(), SQLite is empty on a fresh deploy. Each instance hydrates the low-frequency set + admin datasets from Prisma — boot is the ONLY Prisma → SQLite flow (opts.boot: leaderBypass pull, skipReconcile, breaker respected). The 6h probe is a one-way SQLite → Prisma PUSH, single-writer via the leader gate.

Key decision: boot PULLS bypass the leader gate (leaderBypass: true — every instance hydrates) but keep the breaker gate — a held Prisma degrades gracefully (log + sync_history error row, retried at the next 6h probe). Boot never pushes (skipReconcile: true); the SQLite→Prisma push remains leader-gated so cold-start bursts never race writes.

4 · Read Paths — Market Data vs Derived Data

Market-data routes touch NSE (throttled) and stop at SQLite — Prisma is never consulted. Derived-data routes serve from the SQLite mirror with Prisma as last-resort fallback.

5 · Low-Frequency Sync — 6h Leader PUSH (one-way)

The only recurring Prisma↔SQLite sync is the 6h leader-gated probe, and it is SQLite → Prisma ONLY (per user directive): the _sync_outbox change queue drains tracked SQLite writes into Prisma chunked, the control plane is reconciled, and every run is recorded in sync_history. Boot hydration (section 3) is the ONLY Prisma → SQLite flow.

Why “only low-frequency”: the 60s NSE→Prisma promote timer is removed, and the 3 flushNseToPrisma() write-mirror calls in sync services are deleted. NSE data stops at SQLite; the 6h push is what keeps Prisma daily_prices and every other consumer fresh — new/changed bars only (per-symbol outbox markers, not per-bar rows). Jobs and admin CRUD write SQLite + outbox at runtime; Prisma receives them at the push. Prisma op count drops dramatically — closer to the <1000/day target.

7 · NSE Anti-Blacklist Discipline

NEW lib/services/nseRateGuard.ts — memory-only, zero DB. Wired into nseFetch, lib/nse-api.ts fetchers, and the market-cache chain.

GuardMechanismDefault limits
Single-flightConcurrent identical NSE requests share one in-flight promise (nseInflight: Map<key, Promise>)per method+path
Min-interval throttlePer-endpoint-key minimum spacing (nseLastCall); skip if too soonquote 1s · chart 5s · historical 250ms · index 2s · corp actions 30s · marquee 30s
Stale-while-revalidateServe SQLite/memory snapshot immediately; refresh in backgroundexisting enhancedCache.getWithCache pattern
Burst cooldown≥5 × 403/419/429 within 60s → 60s backoff, serve SQLite/stale onlyNSE_THROTTLE_MS env override (dev)
Boot staggerHistorical sync keeps 200ms inter-symbol delay; market-sync keeps 6-min budgetunchanged
Net result: route bursts collapse to one real NSE call; cooldown mode never blacklists us; users see live or slightly-stale data instead of 502s.

9 · Implementation Order

  1. Phase 0 — WASM build fix (prod SQLite Ready) — prerequisite
  2. Phase 1 — sync_history table + recording + db-health history persistence
  3. Phase 2 — boot hydration opts (reason:"boot", skipReconcile, leaderBypass — every instance hydrates)
  4. Phase 3 — NSE rate guard (single-flight / throttle / cooldown)
  5. Phase 4 — _sync_outbox table + pushSqliteToPrisma() engine + 6h probe pivot (PUSH, not pull)
  6. Phase 5 — NSE captures → SQLite + outbox markers; remove auto-promote (timer + 3 flush call sites)
  7. Phase 6 — jobs write SQLite-first (recs / swing / perf: mirror parity validation + write-through helpers)
  8. Phase 7 — admin datasets SQLite-first (announcements / corp-actions / alerts / holdings) + getSqliteDerived()
  9. Phase 8 — db-health Outbox section + “Push to Prisma” button + sync-history columns
  10. Phase 9 — full verification gate (tsc 46 baseline · Jest suite · Playwright · docs)
Risks / open questions (for human approval)
  • R1 Multi-instance freshness (accepted tradeoff): SQLite-first job/admin writes are locally fresh; other instances’ mirrors refresh at boot + memory cache until the 6h push. Phase-9 mitigation option: publish-on-write for job rows (not in scope).
  • R2 daily_price marker rewrite volume: each 6h push rewrites the full bar history of marked symbols (idempotent, chunked) — fine at current sizes.
  • R3 Admin outbox vs co-writer overlap: alert lifecycle / announcement broadcast tasks keep Prisma write-through; a same-row admin outbox push wins (rare).
  • R4 transaction boot-hydration volume: cap mirrored rows to the admin-holdings display scope (confirm during implementation).
  • Q1 Boot vs breaker: leaderBypass + skipReconcile (every instance pulls; breaker respected) rather than bare force:true — a held Prisma shouldn't cascade a boot failure.
  • Q2 ai_config mirror: value-masked is_set flag only; the API key value never lands in SQLite; config edits stay Prisma, mirrored at boot only.
  • Q3 user_session mirror: metadata-only; Prisma stays authoritative for validation.
  • Q4 .next pruning: verify sql-wasm.wasm survives the Netlify build on the first deploy after Phase 0.
