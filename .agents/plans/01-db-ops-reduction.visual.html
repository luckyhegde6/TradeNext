TradeNext — DB Ops Reduction

Cold-start Netlify bursts were multiplying Prisma ops 5–10×. Fix: single-writer leader election + a SQLite write-behind log store (14-day TTL) that promotes only important rows to Prisma in ONE createMany — target <1000 Prisma ops/day.

v3.22.0 · feat/db-health-ops-visibility 5 instances × worker/cron/sync leader-<role> lock on worker_status write-behind SQLite wb_* tables isWbImportant promotion 15-min leader-gated flush

1 · The Problem

2026-09-02 prod evidence: a cold-start burst of ~5 Netlify instances each booted a worker engine, a cron daemon, and an 8–10× syncFromPrisma() reading all 10 tables — pushing Prisma far past the plan limit and tripping the breaker.

Prod evidenceRoot cause
"Plan limit circuit breaker open" 04:54–05:15✕ Every instance ran full worker + cron + sync.
"APIRequestLog.upsert timed out after 120000ms"✕ Every API request wrote a log row directly to Prisma.
"WorkerTask.findMany timed out"✕ 30s poll from each instance.
each instance totalRows=2034-2056, durationMs=~7000⚠ Duplicate full-table syncs; memory ~460 MB / instance.
User directive: audit and slash every non-essential Prisma call; logs are high-frequency writes → move them to a durable local store and promote only what matters.

2 · Single-Writer Leader Election

lib/services/leader.ts — a lock row worker_status name leader-<role> (cron-daemon | worker | sqlite-sync) with a 5-min staleness window and 60s heartbeat. Only the elected instance runs the cron scheduler, the worker poll, and the SQLite sync; standbys stand down. DB down → fail-open local leader, re-elect on recovery.

    else all rows fresh (no stale claim)
        A->>DB: insert leader-worker-<host>-<pid>
        alt insert ok (unique)
            DB-->>A: leader
        else P2002 — someone else won
            DB-->>A: stand-by (degrade local, no duplicate jobs)
        end
    end
    B->>DB: acquireLeaderLock fails / not needed → standby
    C->>DB: standby
    Note over A,DB: OnLost (renew returned false) → stopWorkerEngine / stopCronDaemon
so stale leaders never keep polling
Key decision: the atomic updateMany claim on a stale row is the primary path — it removes the creation race entirely. Genuine non-conflict create errors rethrow (never silently stand down); only claim-step races stand down.

3 · SQLite Write-Behind Log Store

API/audit/server log rows enqueue to SQLite (wb_api_request · wb_server_log · wb_audit_log) synchronously — zero Prisma ops. A 15-min leader-gated flush drains in chunks, promotes only isWbImportant() rows in ONE createMany, prunes to 14 days.
